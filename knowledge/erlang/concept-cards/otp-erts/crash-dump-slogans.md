# Quick Definition

The crash dump slogan is the first and most important piece of information in a crash dump, appearing as `Slogan: <reason>`. It describes why the crash occurred. If `erlang:halt/1` was called with a string argument, the slogan is that string; otherwise it is a description generated by the emulator or the Erlang kernel.

# Core Definition

The slogan appears at the beginning of the crash dump file and indicates the reason for the dump. "Normally the message is enough to understand the problem" (Ericsson AB, "How to Interpret the Erlang Crash Dumps," section "Reasons for Crash Dumps"). The source cautions that suggested reasons are "only suggestions" -- exact causes can vary depending on local applications and the underlying operating system.

Common slogans and their meanings:

**Memory allocation failures:**
- `<A>: Cannot allocate <N> bytes of memory (of type "<T>")` -- The system ran out of memory. `<A>` is the allocator, `<N>` is the byte count, and `<T>` is the memory block type. Common types include `heap`, `old_heap`, `heap_frag`, and `binary`, usually indicating a process storing huge amounts of data.
- `<A>: Cannot reallocate <N> bytes of memory (of type "<T>")` -- Same as above but during reallocation.

**Code/application errors:**
- `Unexpected op code <N>` -- Error in compiled code, damaged `.beam` file, or compiler error.
- `Module <Name> undefined | Function <Name> undefined | No function <Name>:<Name>/1 | No function <Name>:start/2` -- Damaged Kernel/STDLIB applications or damaged start script.

**System limits:**
- `Driver_select called with too large file descriptor N` -- File descriptor count exceeds 1024 (Unix only), due to limitations in the Unix `select` call. Only sockets/pipes are affected, not regular files.

**Signals:**
- `Received SIGUSR1` -- A `SIGUSR1` signal was sent to force a crash dump (Unix only).

**Kernel/boot failures:**
- `Kernel pid terminated (<Who>) (<Exit reason>)` -- The kernel supervisor detected a failure. Most commonly, the `application_controller` shut down because the node name is already in use, or a complete supervisor tree crashed.
- `Init terminating in do_boot ()` -- Boot sequence terminated, usually a configuration error such as a faulty `-boot` parameter or boot script from the wrong OTP version.
- `Could not start kernel pid (<Who>) ()` -- A kernel process could not start, probably due to faulty arguments (e.g., errors in `-config`) or faulty configuration files.

# Key Properties

1. The slogan is the first thing to read when analyzing a crash dump
2. Memory allocation slogans include the allocator name, byte count, and memory type
3. Kernel pid termination slogans often indicate application-level failures, not VM bugs
4. The slogan can be any string if generated by `erlang:halt/1`
5. Boot-related slogans typically indicate configuration problems
6. Slogans not in the documented list may still be application-related (from `erlang:halt/1`)
7. If the slogan is not from `erlang:halt/1` and not in the known list, it could indicate an emulator error

# Construction / Recognition

## Reading the Slogan

The slogan appears near the top of the crash dump:

```text
Slogan: <A>: Cannot allocate <N> bytes of memory (of type "<T>")
```

## Diagnosing from the Slogan

1. **Memory slogans** (`Cannot allocate/reallocate`): Check process heap sizes, ETS table sizes, and binary usage in the crash dump. Look for the allocator type `<T>` to narrow down the source.
2. **Kernel pid terminated**: Check application error logs first. Look at the `<Who>` and `<Exit reason>` fields. If `Who` is `application_controller` and `Why` is `shutdown`, check if the node name is already in use.
3. **Init terminating in do_boot**: Verify the `-boot` parameter and boot script OTP version compatibility.
4. **Could not start kernel pid**: Check `-config` arguments and configuration file integrity.
5. **Received SIGUSR1**: This is an intentional diagnostic dump, not a real crash.

# Context & Application

The slogan is the entry point for all crash dump analysis. In production environments:

- Memory allocation failures are the most common crash reason and indicate that a process is accumulating too much data (large heaps, binaries, or message queues)
- Kernel supervisor crashes often point to distributed Erlang issues (duplicate node names) or complete supervisor tree failures
- Boot failures are typically deployment/configuration issues
- The `SIGUSR1` slogan is used intentionally for diagnostic purposes and should not trigger incident response

After identifying the slogan category, the next step is usually to examine process information, ETS tables, or memory allocation details in the crash dump to find the root cause.

# Examples

**Memory exhaustion slogan** (source: "How to Interpret the Erlang Crash Dumps," section "Reasons for Crash Dumps"):

```text
Slogan: ets_alloc: Cannot allocate 1048576 bytes of memory (of type "heap")
```

This indicates the `ets_alloc` allocator failed to allocate about 1 MB for a heap. A process is likely storing excessive data.

**Kernel pid terminated** (source: same section):

```text
Slogan: Kernel pid terminated (application_controller) (shutdown)
```

The application controller shut down -- commonly caused by a duplicate node name in distributed Erlang.

**Forced diagnostic dump** (source: same section):

```text
Slogan: Received SIGUSR1
```

An operator intentionally triggered the crash dump for diagnostic purposes.

# Common Errors

- **Error**: Treating every crash dump as a VM bug
  **Correction**: Most slogans indicate application-level or configuration issues. Memory exhaustion, duplicate node names, and boot script errors are all application/deployment problems.

- **Error**: Ignoring the `<T>` (type) field in memory allocation slogans
  **Correction**: The type (heap, old_heap, heap_frag, binary) narrows down the source of memory pressure significantly

- **Error**: Not checking application error logs alongside the crash dump for kernel pid termination slogans
  **Correction**: The source explicitly recommends "looking at the error log for your application" as "probably the first step to take" for kernel supervisor failures

# Common Confusions

- **Confusion**: `Received SIGUSR1` means the system crashed
  **Clarification**: This slogan indicates an intentional diagnostic dump triggered by an operator sending SIGUSR1 to the Erlang process

- **Confusion**: An unknown slogan must be a VM error
  **Clarification**: `erlang:halt/1` can generate any message as a slogan, so unknown slogans may come from application code

- **Confusion**: `Driver_select called with too large file descriptor N` means too many files are open
  **Clarification**: Only sockets and pipes are limited to 1024 by the Unix `select` call; regular file opens are not affected by this limit
