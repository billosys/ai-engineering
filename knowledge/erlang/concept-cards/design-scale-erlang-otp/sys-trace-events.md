# Quick Definition

Sys trace and log events are the debug-output mechanism a special process uses: it initializes debug options with `sys:debug_options/1`, carries them in its loop data, and emits trace events with `sys:handle_debug/4`.

# Core Definition

Special processes can accept debug flags — `trace`, `log`, `statistics`, `{log_to_file, FileName}` — passed in their start call's `DbgOpts` argument (Cesarini & Vinoski, p. 248). This list is passed to `sys:debug_options(DbgOpts)`, which initializes the debug routines; its return value is kept in the process's loop data and passed to all system calls. Trace events are generated by calling `sys:handle_debug(Debug, DbgFun, Extra, Event)`, where `DbgFun` is an arity-3 fun that formats the event, `Extra` is data used during formatting (often the process name or loop data), and `Event` is the event to print. Trace requests from `sys:trace/3`, `sys:log/2`, and similar calls arrive as system messages; `handle_debug/4` returns an updated `Debug` value (pp. 248-250).

# Prerequisites

- **Special process** — Trace and log events are an optional capability of a special process.

# Key Properties

1. Debug flags (`trace`, `log`, `statistics`, `{log_to_file, FileName}`) are passed in the start call's `DbgOpts`.
2. `sys:debug_options(DbgOpts)` initializes debug routines; its result is stored in loop data.
3. Trace events are emitted with `sys:handle_debug(Debug, DbgFun, Extra, Event)`.
4. `DbgFun` is an arity-3 fun receiving the I/O device, `Extra`, and `Event`.
5. `handle_debug/4` returns an updated `Debug` to pass to the next loop iteration.
6. Trace/log control requests (`sys:trace/3`, `sys:log/2`) arrive and are handled as system messages.
7. Custom trace functions can be installed at runtime with `sys:install/2`.

# Construction / Recognition

## To Construct/Create:
1. Accept `DbgOpts` in the start call; pass it to `sys:debug_options/1` in `init`.
2. Store the returned `Debug` in loop data.
3. On each handled event, call `sys:handle_debug(Debug, fun debug/3, Name, Event)` and carry the new `Debug` forward.

## To Identify/Recognize:
1. A `sys:debug_options/1` call in `init`.
2. `sys:handle_debug/4` calls in the process loop.

# Context & Application

- **Typical contexts**: Debugging and tracing special processes at runtime.
- **Common applications**: Turning trace/log on or off at runtime; diverting trace to a file; retrieving status with `sys:get_status/1`.
- **Historical/stylistic notes**: The book ties this to the Chapter 5 discussion of tracing and logging OTP behaviors — the same `sys` facilities apply to special processes (p. 248).

# Examples

**Example 1** (pp. 249-250): The mutex calls `sys:handle_debug(Debug, fun debug/3, Name, {wait,Pid})`; the `debug/3` fun does `io:format(Dev, "mutex ~w: ~w~n", [Name,Event])`.

**Example 2** (p. 250): Shell run starting the mutex with the `trace` flag, then using `sys:log/2`, `sys:statistics/2`, and `sys:get_status/1`.

## Worked Example

Initializing and emitting trace events (pp. 248-249):

```erlang
init(Parent, Name, DbgOpts) ->
    ...
    Debug = sys:debug_options(DbgOpts),
    proc_lib:init_ack({ok,self()}),
    NewDebug = sys:handle_debug(Debug, fun debug/3, Name, init),
    free(Name, Parent, NewDebug).

debug(Dev, Event, Name) ->
    io:format(Dev, "mutex ~w: ~w~n", [Name,Event]).
```

# Common Errors

- **Error**: Discarding the `Debug` value returned by `sys:handle_debug/4`.
  **Correction**: Carry the updated `Debug` into the next loop iteration; trace state changes between calls.

- **Error**: Initializing the process without `sys:debug_options/1`.
  **Correction**: Call it on the `DbgOpts` list so trace/log/statistics requests can be honored later.

# Common Confusions

- **Confusion**: Thinking trace output is built into special processes automatically.
  **Clarification**: Trace and log support is optional and must be wired in explicitly via `sys:debug_options/1` and `sys:handle_debug/4`.
