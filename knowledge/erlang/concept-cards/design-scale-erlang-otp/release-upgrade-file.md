# Quick Definition

A release upgrade file (`relup`) contains all the low-level commands executed during a release upgrade. It is generated by `systools:make_relup/3,4` from the new and old `.rel` files and the applications' `.appup` files.

# Core Definition

The release upgrade file, called `relup`, is generated using the emulator and application versions specified in the `.rel` and `.appup` files, using them to retrieve and map high- and low-level instructions in the `.appup` files to a sequence of low-level ones (Cesarini & Vinoski, p. 339-341, pdf p. 336). It is created by `systools:make_relup(RelName, UpFromList, DownToList, [Options])` and placed in the current working directory (or `{outdir, Dir}`). Its format is `{Vsn, [{UpFromV, Descr, InstructionsU}, ...], [{DownToV, Descr, InstructionsD}, ...]}` — similar to the `.appup` file but with a `Descr` term and only low-level instructions.

# Prerequisites

- **Application upgrade file** — `.appup` files are inputs that generate the `relup`; that concept comes first.
- **Release resource file** — The new and old `.rel` files supply the version information.

# Key Properties

1. Named `relup`; holds all low-level commands executed during the upgrade.
2. Generated by `systools:make_relup(RelName, UpFromList, DownToList, [Options])`.
3. Inputs: new and old `.rel` files (versions) and `.appup` files (instructions).
4. Format: `{Vsn, [{UpFromV, Descr, InstructionsU}], [{DownToV, Descr, InstructionsD}]}`.
5. `Descr` is a term from the `{RelName, Descr}` tuple; defaults to an empty list.
6. Contains only low-level instructions (high-level `.appup` actions are translated).
7. `make_relup` options: `{path, DirList}`, `{outdir, Dir}`, `restart_emulator`, `silent`, `noexec`, `warnings_as_errors`.
8. The node's code path must include the old and new `.rel`/`.app` files and the new `.appup`/`.beam` files.
9. Not used for the upgrade itself directly — it is executed by `release_handler:install_release/1`.

# Construction / Recognition

## To Create a relup File:
1. Compile the new application code and write its `.appup` file into `ebin`.
2. Call `systools:make_relup("NewRel", ["OldRel"], ["OldRel"], [{path, [...]}])`.
3. The `relup` file is written to the working directory (or `{outdir, Dir}`).
4. `systools:make_tar/2` picks it up automatically when packaging the upgrade.

## To Recognize It:
1. A file named `relup` in a release's `releases/Vsn` directory.
2. It holds a `{Vsn, [...], [...]}` tuple of low-level instructions.

# Context & Application

- **Typical contexts**: Generating the executable upgrade script for a release upgrade.
- **Common applications**: Packaged into the upgrade tar; executed by `release_handler:install_release/1`.
- **Historical/stylistic notes**: A `relup` generated by `rebar3` is identical to one generated by `systools:make_relup/4`.

# Examples

**Example 1** (p. 340): The generated coffee `relup` file:

```erlang
{"1.1",
 [{"1.0",[],
   [{load_object_code,{coffee,"1.1",[coffee_fsm]}},
    point_of_no_return,
    {suspend,[coffee_fsm]},
    {load,{coffee_fsm,brutal_purge,brutal_purge}},
    {code_change,up,[{coffee_fsm,{}}]},
    {resume,[coffee_fsm]}]}],
 [{"1.0",[],
   [{load_object_code,{coffee,"1.0",[coffee_fsm]}},
    point_of_no_return,
    {suspend,[coffee_fsm]},
    {code_change,down,[{coffee_fsm,{}}]},
    {load,{coffee_fsm,brutal_purge,brutal_purge}},
    {resume,[coffee_fsm]}]}]}.
```

**Example 2** (p. 339): Generating it: `systools:make_relup("coffee-1.1", ["coffee-1.0"], ["coffee-1.0"], [{path, ["coffee*/ebin"]}])`.

# Relationships

## Builds Upon
- **Application upgrade file** — `.appup` files are translated into the `relup`.
- **Release resource file** — The old/new `.rel` files supply version information.

## Related
- **Low-level instructions** — The `relup` contains only low-level instructions.
- **High-level instructions** — High-level `.appup` actions are mapped into the `relup`.
- **systools** — `make_relup/3,4` generates the `relup`.
- **Release handler** — Executes the `relup` via `install_release/1`.

## Contrasts With
- **Application upgrade file** — The `.appup` is per-application and may hold high-level instructions; the `relup` is per-release and holds only low-level ones.

# Common Errors

- **Error**: Generating the `relup` without the old and new `.rel`/`.app`/`.appup` files on the code path.
  **Correction**: Ensure the node's code path includes paths to both old and new `.rel`/`.app` files plus the new `.appup` and `.beam` files.

- **Error**: Expecting the `relup` to be executed on its own.
  **Correction**: The `relup` is run by `release_handler:install_release/1`; it is packaged into the upgrade tar, not executed standalone.

# Common Confusions

- **Confusion**: Thinking the `relup` is used to boot a node.
  **Clarification**: The `relup` drives upgrades; a separate boot file is generated for rebooting an upgraded node.

- **Confusion**: Believing the `relup` can contain high-level instructions.
  **Clarification**: The `relup` holds only low-level instructions; high-level `.appup` actions are translated during generation.
