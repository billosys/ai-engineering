# Quick Definition

`throw`, `exit`, and `error` are the three BIFs that explicitly raise an exception; they differ in intent — `throw` for catchable, documented exceptions, `exit` for terminating a process, and `error` for crashing errors.

# Core Definition

An exception can be explicitly generated by calling one of three BIFs ("Error Handling in Sequential Programs", *Handling Errors in Sequential Code*):

- **`exit(Why)`** — used when you really want to terminate the current process. If not caught, the signal `{'EXIT', Pid, Why}` is broadcast to all processes linked to the current process.
- **`throw(Why)`** — used to throw an exception that a caller might want to catch. The function should *document* that it might throw this exception; the caller may either program for the common case and ignore exceptions, or enclose the call in a `try...catch`.
- **`error(Why)`** — used to denote "crashing errors": something rather nasty has happened that callers are not really expected to handle. This is on par with internally generated errors.

# Prerequisites

- **Exception** — These BIFs are the explicit means of raising an exception, so the exception concept is required.

# Key Properties

1. `throw/1` signals a catchable, documented exception meant for the caller.
2. `exit/1` terminates the current process and (if uncaught) broadcasts `{'EXIT', Pid, Why}` to linked processes.
3. `error/1` signals a crash-level error not expected to be handled; it ranks with runtime-generated errors.
4. Each BIF produces an exception of the corresponding class (`throw`, `exit`, `error`).
5. All three take a single argument — an arbitrary term describing the reason.

# Construction / Recognition

## To Construct/Create:
1. `throw(Why)` to raise a recoverable exception.
2. `exit(Why)` to terminate the process.
3. `error(Why)` to signal a crashing error.

## To Identify/Recognize:
1. In a caught exception, the class atom (`throw`, `exit`, or `error`) tells you which BIF (or the runtime) generated it.

# Context & Application

- **Typical contexts**: `throw` in functions where errors are possible but rare; `error` to improve error messages; `exit` to deliberately stop a process.
- **Common applications**: the `generate_exception` test function in `try_test.erl` raises each of `throw(a)`, `exit(a)`, and `error(a)`.
- **Historical/stylistic notes**: a function that may `throw` should document the exception it throws so callers can decide whether to catch it.

# Examples

**Example 1** (*Programming Idioms with try...catch*): a function exercising all three BIFs:

```erlang
generate_exception(1) -> a;
generate_exception(2) -> throw(a);
generate_exception(3) -> exit(a);
generate_exception(4) -> {'EXIT', a};
generate_exception(5) -> error(a).
```

**Example 2** (*Improving Error Messages*): using `error/1` to raise a clearer message:

```erlang
sqrt(X) when X < 0 ->
    error({squareRootNegativeArgument, X});
sqrt(X) ->
    math:sqrt(X).
```

# Common Errors

- **Error**: Using `error/1` for an exception the caller is expected to handle routinely.
  **Correction**: Use `throw/1` for recoverable, caller-handled exceptions; reserve `error/1` for crashing errors.

- **Error**: Returning the tuple `{'EXIT', a}` and expecting it to behave like `exit(a)`.
  **Correction**: A plain `{'EXIT', a}` tuple is an ordinary return value, not an exception; `exit(a)` actually raises one.

# Common Confusions

- **Confusion**: Believing the three BIFs are interchangeable.
  **Clarification**: They differ in intent and in the exception class produced; `throw` is catchable-by-design, `exit` terminates the process, `error` is crash-level.

- **Confusion**: Thinking `exit/1` only affects the current process.
  **Clarification**: An uncaught `exit` also broadcasts an `{'EXIT', Pid, Why}` signal to all linked processes.
