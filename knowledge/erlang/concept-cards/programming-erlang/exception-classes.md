# Quick Definition

Erlang exceptions belong to one of three classes — `throw`, `exit`, or `error` — raised by the BIFs `throw/1`, `exit/1`, and `error/1` respectively. The class signals intent and is matched in the `catch` part of a `try...catch`.

# Core Definition

An exception can be explicitly generated by calling one of three BIFs, each producing a different exception class:

- `exit(Why)` — used when you really want to terminate the current process. If uncaught, the signal `{'EXIT', Pid, Why}` is broadcast to all linked processes.
- `throw(Why)` — used to throw an exception that a caller might want to catch. You *document* that the function might throw it; callers can program for the common case and ignore it, or wrap the call in `try...catch`.
- `error(Why)` — used for "crashing errors": something nasty has happened that callers are not expected to handle, on par with internally generated errors.

In a `try...catch`, the `ExceptionType` is an atom — one of `throw`, `exit`, or `error` — that tells how the exception was generated. If the type is omitted in a catch clause it defaults to `throw`. Internal errors detected by the Erlang runtime always have the tag `error` ("Error Handling in Sequential Programs," *Handling Errors in Sequential Code*; *Trapping an Exception with try...catch*).

# Key Properties

1. There are exactly three classes: `throw`, `exit`, `error`.
2. `throw/1` — for exceptions a caller might catch; the function should document it.
3. `exit/1` — for terminating the current process; uncaught, it sends `{'EXIT', Pid, Why}` to linked processes.
4. `error/1` — for crashing errors not expected to be handled.
5. Runtime-detected internal errors always have class `error`.
6. In a `catch` clause, an omitted exception type defaults to `throw`.

# Construction / Recognition

## To Construct/Create:
1. Choose the class by intent: `throw` (catchable, documented), `exit` (terminate process), `error` (crash).
2. Call the corresponding BIF, e.g. `throw({thisError, X})`.

## To Identify/Recognize:
1. In `try...catch`, write `ExceptionType:Pattern -> ...` where `ExceptionType` is `throw`, `exit`, or `error`.
2. A clause with no type, e.g. `_ -> ...`, only catches the default class `throw`.

# Context & Application

- **Typical contexts**: Choosing how to signal a failure based on whether the caller should handle it.
- **Common applications**: `error({squareRootNegativeArgument, X})` to produce a clearer crash message; `throw({thisError, ...})` for expected, recoverable conditions.
- **Historical/stylistic notes**: Using `throw` for control flow is documented behavior between a function and its caller.

# Examples

**Example 1** (*Programming Idioms with try...catch*): A function raising all three classes.

```erlang
generate_exception(2) -> throw(a);
generate_exception(3) -> exit(a);
generate_exception(5) -> error(a).
```

**Example 2** (*Programming Idioms with try...catch*): A catch block distinguishing the three classes.

```erlang
catch
    throw:X -> {N, caught, thrown, X};
    exit:X  -> {N, caught, exited, X};
    error:X -> {N, caught, error, X}
end.
```

**Example 3** (*Improving Error Messages*): Using `error/1` to produce a better message.

```erlang
sqrt(X) when X < 0 ->
    error({squareRootNegativeArgument, X});
sqrt(X) ->
    math:sqrt(X).
```

# Common Errors

- **Error**: Writing `try Expr catch _ -> ... end` and expecting it to catch everything.
  **Correction**: An omitted type defaults to `throw`; use `_:_ -> ...` to catch every class.

- **Error**: Using `exit/1` when you only want the caller to recover.
  **Correction**: Use `throw/1` for caller-handleable exceptions; reserve `exit/1` for terminating the process.

# Common Confusions

- **Confusion**: Thinking the three classes are interchangeable.
  **Clarification**: They signal different intents — `throw` for documented catchable exceptions, `exit` for process termination, `error` for crashing errors and runtime faults.

- **Confusion**: Believing runtime errors can have any class.
  **Clarification**: Internal errors detected by the runtime always have the class `error`.
