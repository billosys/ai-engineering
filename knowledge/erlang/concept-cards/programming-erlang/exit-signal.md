# Quick Definition

An exit signal is the special signal automatically broadcast to a process's link set when it terminates; it carries an exit reason describing why the process died. Processes can also send "fake" exit signals explicitly with `exit/2`.

# Core Definition

Processes collaborate by exchanging *messages* or *error signals*. Error signals are sent automatically when a process crashes or terminates, and they are sent to the *link set* of the terminated process (Chapter 13, "Error Handling Semantics"). When a system process receives an error signal, the signal is converted into a message of the form `{'EXIT', Pid, Why}`, where `Pid` is the identity of the terminated process and `Why` is the *exit reason*. If a process terminates without error, `Why` is the atom `normal`; otherwise `Why` describes the error. When a normal (non-system) process receives an error signal, it terminates if the exit reason is not `normal`, and on terminating it broadcasts an exit signal to its own link set. A process can also send signals explicitly: `exit(Why)` terminates the current process and broadcasts the signal; `exit(Pid, Why)` sends a "fake" exit signal to `Pid` without the caller dying. The *kill signal*, generated by `exit(Pid, kill)`, is untrappable — it bypasses the normal signal processing and is not converted into a message even for system processes.

# Prerequisites

- **Process** — Exit signals are sent by and to processes.
- **Link** — Exit signals propagate along link sets, so links must be understood first.

# Key Properties

1. Exit signals are sent automatically when a process crashes or terminates.
2. They are delivered to the terminated process's link set.
3. A system process converts a received signal into the message `{'EXIT', Pid, Why}`.
4. A normal process receiving an abnormal signal dies and re-broadcasts to its own link set.
5. Exit reason `normal` indicates a clean termination and does not kill a normal process.
6. `exit(Why)` self-terminates and broadcasts; `exit(Pid, Why)` sends a fake signal without the caller dying.
7. `exit(Pid, kill)` produces an untrappable kill signal — even system processes cannot trap it.

# Construction / Recognition

## To Send an Exit Signal:
1. To terminate yourself and notify your link set, call `exit(Why)`.
2. To send a fake exit signal to another process, call `exit(Pid, Why)`.
3. To forcibly terminate a rogue process, call `exit(Pid, kill)`.

## To Recognize Exit-Signal Handling:
1. Look for `receive` clauses matching `{'EXIT', Pid, Why}` (in system processes).
2. Look for processes dying in groups when one of a linked set crashes.

# Context & Application

- **Typical contexts**: Error propagation in concurrent and distributed Erlang.
- **Common applications**: Tearing down groups of linked processes; faking errors to control other processes; killing unresponsive processes.
- **Historical/stylistic notes**: The kill signal "should be reserved for rogue processes that refuse to die using any of the other error handling mechanisms."

# Examples

**Example 1** (Chapter 13, "Explicit error signals"): A process evaluating `exit(Why)` outside the scope of `catch`/`try` terminates and broadcasts an exit signal with reason `Why` to its link set.

**Example 2** (Chapter 13, "Explicit error signals"): `exit(Pid, Why)` sends `Pid` a fake exit signal with reason `Why`; the process that called `exit/2` does not itself die — "this is deliberate."

**Example 3** (Chapter 13, error report): Sending the atom `hello` to a process running `list_to_atom(X)` crashes it; the system error handler reports the exit value `{badarg,[{erlang,list_to_atom,[hello],[]}]}` — the exit reason describing the error.

# Relationships

## Builds Upon
- **Link** — exit signals propagate along link sets.

## Enables
- **Trapping exits** — a system process traps exit signals by converting them to `{'EXIT', Pid, Why}` messages.

## Related
- **Monitor** — a monitored process's death carries the same exit reason `Why` in a `'DOWN'` message.
- **Error handling philosophy** — exit signals are the propagation mechanism for remote error handling.

## Contrasts With
- **Message passing** — ordinary messages go to one named process; error signals are broadcast automatically to a link set and can kill the receiver.

# Common Errors

- **Error**: Expecting `exit(Pid, kill)` to be trappable by a system process.
  **Correction**: The kill signal is untrappable; reserve it for genuinely rogue processes.
- **Error**: Assuming `exit(Pid, Why)` kills the caller.
  **Correction**: `exit/2` sends a signal to `Pid` only; the caller survives.

# Common Confusions

- **Confusion**: An exit signal with reason `normal` kills linked processes.
  **Clarification**: A normal process receiving a `normal` exit signal does not die; only abnormal reasons kill non-system processes.
- **Confusion**: Exit signals and messages are the same thing.
  **Clarification**: Messages are sent with `send`/`!`; exit signals are sent automatically on termination and are converted to messages only for system processes.
