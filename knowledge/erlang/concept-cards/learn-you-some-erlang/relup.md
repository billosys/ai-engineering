# Relup

## Quick Definition

A relup (release upgrade) is a file containing instructions to upgrade an entire running Erlang release from one version to another while it runs. It is generated from the old and new releases and their applications' appup files.

## Core Definition

The book defines relups as "files containing instructions to update an entire release" (Ch. 22). The relup is the file produced by `systools:make_relup/3`, which combines the appup instructions of all applications in a release. The chapter warns that relups are "one of the most complex parts of OTP," hard to comprehend, get right, and time-consuming, and recommends avoiding them in favor of rolling restarts whenever possible (Ch. 22, "The Ninth Circle of Erl").

## Prerequisites

- **Appup** — Each application needs an appup; the relup is generated from them
- **Erlang-release** — Relups upgrade releases, so a release must exist first

## Key Properties

1. A relup is generated by `systools:make_relup(NewRel, [UpFromRels], [DownToRels])`
2. The release must be built with debug info and with no `.ez` archive (the upgrade tools cannot look inside `.ez` files)
3. SASL must be included in the release, or upgrading the system is impossible
4. A `RELEASES` file must be created (via `release_handler:create_RELEASES/4`) before starting production, or you cannot roll back to the first release
5. Installation proceeds: `release_handler:unpack_release/1`, `release_handler:install_release/1`, `release_handler:make_permanent/1`
6. Downgrades are done with `release_handler:install_release(OldVersion)`
7. Relups are messy, error-prone, and Ericsson divisions reportedly spend as much time testing relups as testing their applications

## Construction / Recognition

### To perform a relup (summary from "Relup Review")

1. Write and compile OTP applications; build release 1.0.0 with Reltool (debug info, no `.ez`)
2. Create the `RELEASES` file before starting production
3. Run the release, find and fix bugs in new application versions
4. Write appup files for each changed application; compile the new applications
5. Build the new release; copy `.rel`/`.boot` files into versioned names
6. Generate the relup with `systools:make_relup/3`; move it into `rel/releases/Vsn`
7. Generate a release tar with `systools:make_tar/1`; move it to `rel/releases/`
8. From a shell still running the old release: `release_handler:unpack_release`, `install_release`, `make_permanent`
9. Verify; roll back by installing an older version if needed

## Context & Application

Relups are for products that "can imperatively never be shut down." The book recommends doing simple rolling upgrades (restart VMs, boot new applications) whenever you can avoid relups. Tools like rebar can automate some of the painful steps.

## Examples

**Example** (Ch. 22): Generating the Process Quest relup —

```erlang
1> systools:make_relup("./rel/releases/1.1.0/processquest-1.1.0",
1>                     ["rel/releases/1.0.0/processquest-1.0.0"],
1>                     ["rel/releases/1.0.0/processquest-1.0.0"]).
ok
```

**Example** (Ch. 22): After `make_permanent("1.1.0")`, `sockserv`'s socket `gen_server`s die because they were blocked in `gen_tcp:accept` and could not process the upgrade — illustrating that blocked processes are killed during a relup.

## Relationships

### Builds Upon

- **Appup** — A relup aggregates per-application appup instructions
- **Erlang-release** — Relups transition one release version to another

### Related

- **Release-handler** — The module that unpacks, installs, and makes a relup permanent
- **Hot-code-loading** — Relups orchestrate hot loading across an entire release

### Contrasts With

- **Rolling-upgrade** — Restarting VMs with new code instead of an in-place release upgrade

## Common Errors

- **Error**: Forgetting to create the `RELEASES` file before starting the production application.
  **Correction**: Call `release_handler:create_RELEASES/4` first, or you cannot downgrade to the first release (you will see an empty list in `which_releases()`).
- **Error**: Building the release with stripped `debug_info` or as a `.ez` archive.
  **Correction**: Keep `debug_info` and use `{excl_archive_filters, [".*"]}` so no `.ez` is generated.

## Common Confusions

- **Confusion**: Thinking relups are the normal way to upgrade Erlang systems.
  **Clarification**: They are a last resort; rolling restarts are recommended when feasible.
- **Confusion**: Believing a relup automatically upgrades every process safely.
  **Clarification**: Processes blocked on operations like `gen_tcp:accept` cannot upgrade and may be killed.
