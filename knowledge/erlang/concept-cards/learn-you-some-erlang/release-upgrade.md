# Release Upgrade

## Quick Definition

A release upgrade is the process of moving a running release from one version to another without downtime — applying new code to a live system rather than restarting it.

## Core Definition

Chapter 21 *foreshadows* release upgrades rather than implementing them: "what could make your operations guy happier than no downtime? The next challenge will be to do software upgrades while a release is running" (Ch. 21, "Released from Releases"). The chapter establishes that releases enable "a lot of safe control in detecting conflicts and handling live upgrades without shutting your applications down" (Ch. 19), and the `vsn` field of an application "is used to identify your application's version" when "you start using tools to help with upgrades and downgrades."

## Prerequisites

- **Erlang release** — Upgrades move a release between versions.
- **Release resource file** — Upgrades compare `.rel` files / versions across releases.

## Key Properties

1. The goal is to apply new code to a running system with no downtime.
2. Application and release versions (`vsn`) are how upgrade tooling identifies what changed.
3. OTP releases are explicitly designed to support live upgrades and conflict detection.
4. The book treats the detailed mechanics as a topic beyond its scope (a "next challenge").

## Construction / Recognition

## Recognising the Upgrade Path

1. Bump the `vsn` of changed applications and the release.
2. Build the new release with the same tooling (`systools` / Reltool).
3. Use OTP's upgrade tooling to transition the running system between release versions.

## Context & Application

This card sits at the edge of the book's coverage. *Learn You Some Erlang* introduces releases as the foundation that *makes* live upgrades possible but explicitly defers the detailed upgrade procedure. In standard OTP practice, upgrades are driven by *appup* files (per-application upgrade instructions) and a *relup* file (release-level upgrade script generated by `systools:make_relup/3`), applied at runtime by the `release_handler`. The book does not present these mechanics; treat them as the documented OTP feature the chapter points toward.
