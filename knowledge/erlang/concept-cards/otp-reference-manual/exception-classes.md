# Quick Definition

Erlang exceptions come in three classes: `error` (runtime errors or `error/1` calls), `exit` (intentional process termination via `exit/1`), and `throw` (non-local returns via `throw/1`). The `try` expression can distinguish between them; `catch` cannot.

# Core Definition

Exceptions in Erlang are runtime errors or generated errors and belong to three classes. The `error` class originates from runtime errors (e.g., `1+a`) or from calling `error/1`. The `exit` class originates from calling `exit/1`. The `throw` class originates from calling `throw/1`. All three classes can also be generated by calling `erlang:raise/3`. An exception consists of its class, an exit reason, and a stack trace. The `try` expression can distinguish between different exception classes, while the `catch` expression cannot (Erlang Reference Manual, "Errors and Error Handling" chapter, "Exceptions" section).

# Key Properties

1. Three classes: `error`, `exit`, `throw`.
2. `error` — runtime errors or explicit `error(Reason)` calls. Exit reason: `{Reason, Stack}`.
3. `exit` — intentional process exit via `exit(Reason)`. Exit reason: `Reason`.
4. `throw` — non-local return via `throw(Term)`. Must be within a `catch` or `try`/`catch`, otherwise `nocatch` error occurs.
5. `try` can match on all three classes separately; `catch` wraps them differently.
6. `catch` returns: `{'EXIT', {Reason, Stack}}` for `error`, `{'EXIT', Term}` for `exit`, `Term` for `throw`.
7. All classes can be raised with `erlang:raise/3`.
8. Each exception carries a stacktrace.

# Construction / Recognition

## To Raise:
```erlang
error(badarg)      %% class: error
exit(normal)       %% class: exit
throw(my_value)    %% class: throw
erlang:raise(Class, Reason, Stacktrace) %% any class
```

## To Handle (distinguishing classes):
```erlang
try Expr
catch
    error:Reason:Stack -> {runtime_error, Reason, Stack};
    exit:Reason -> {exit, Reason};
    throw:Value -> {thrown, Value}
end
```

## With catch (no class distinction):
```erlang
catch error(test)   %% {'EXIT',{test,[...]}}
catch exit(test)    %% {'EXIT',test}
catch throw(test)   %% test
```

# Context & Application

Understanding exception classes is essential for proper error handling in Erlang. The `error` class signals unexpected failures (bugs, invalid arguments). The `exit` class signals intentional process termination or abnormal conditions that should propagate through process links. The `throw` class provides a mechanism for non-local returns, typically used for anticipated exceptional flow (like early termination of a search). Choosing the right class communicates intent and affects how supervisors and linked processes respond.

# Common Errors

- **Error**: Using `throw/1` outside of any `catch` or `try`/`catch` scope.
  **Correction**: `throw/1` without an enclosing catcher raises a `nocatch` runtime error. Ensure a `catch` or `try`/`catch` is in the call chain.

- **Error**: Using `exit/1` when `error/1` is more appropriate for signaling bugs.
  **Correction**: Use `error/1` for unexpected conditions (bugs) and `exit/1` for intentional process termination.

# Common Confusions

- **Confusion**: Thinking `catch` can distinguish between exception classes.
  **Clarification**: `catch` wraps all exceptions but uses different formats (`{'EXIT',{R,S}}` for errors, `{'EXIT',R}` for exits, bare term for throws). It cannot pattern match on the class. Use `try`/`catch` for class-specific handling.

- **Confusion**: Thinking `exit/1` always terminates the process.
  **Clarification**: `exit/1` raises an exception that can be caught by `try`/`catch`. Only if uncaught does it terminate the process.
