# Quick Definition

Event types in `gen_statem` categorize the different kinds of events that a state callback receives, including external events (`cast`, `{call, From}`, `info`), timeout events (`state_timeout`, `{timeout, Name}`, `timeout`), and self-generated events (`internal`).

# Core Definition

As described in the OTP Design Principles: "Events are categorized in different event types. Events of all types are for a given state handled in the same callback function, and that function gets EventType and EventContent as arguments. The meaning of the EventContent depends on the EventType."

# Prerequisites

- **gen_statem** -- The behaviour that dispatches events with their types to callbacks.
- **State callback** -- The function that receives `EventType` and `EventContent` as arguments.

# Key Properties

1. Every event has an `EventType` and an `EventContent`.
2. The meaning of `EventContent` depends on the `EventType`.
3. All event types for a given state are handled in the same callback function.
4. External event types: `cast`, `{call, From}`, `info`.
5. Timeout event types: `state_timeout`, `{timeout, Name}`, `timeout`.
6. Internal event type: `internal` (can only be generated via `next_event` action).

# Complete List of Event Types

1. **`cast`** -- Generated by `gen_statem:cast/2`. The message becomes EventContent.
2. **`{call, From}`** -- Generated by `gen_statem:call/2` or `gen_statem:send_request/2,4`. The request becomes EventContent. `From` is used for replying.
3. **`info`** -- Generated by any regular process message sent to the gen_statem. The message becomes EventContent.
4. **`state_timeout`** -- Generated when a state timeout expires.
5. **`{timeout, Name}`** -- Generated when a named generic timeout expires.
6. **`timeout`** -- Generated when an event timeout expires.
7. **`internal`** -- Generated only by `{next_event, internal, EventContent}` action. Cannot come from an external source.

# Construction / Recognition

## To Construct/Create:
1. External events are generated by calling `gen_statem:cast/2`, `gen_statem:call/2`, or sending a regular process message.
2. Timeout events are generated by starting timeouts via transition actions and waiting for them to expire.
3. Internal events are generated via the `{next_event, internal, EventContent}` transition action.
4. Any event type can be generated via `{next_event, EventType, EventContent}`.

## To Identify/Recognize:
1. The first argument to the state callback is the EventType.
2. Pattern match on EventType to dispatch: `cast`, `{call, From}`, `info`, `state_timeout`, `{timeout, Name}`, `timeout`, `internal`.

# Context & Application

Event types allow a state callback to distinguish between different sources and kinds of events, enabling appropriate handling. For example, `{call, From}` events require a reply using `{reply, From, Reply}`, while `cast` events do not. Internal events are guaranteed to come from the state machine itself, providing a secure mechanism for self-messaging.

# Examples

**Example 1** (statem.md, "Handling Events"): Handling a cast event:

```erlang
locked(cast, {button,Button}, Data) ->
    ...
```

**Example 2** (statem.md, "All State Events"): Handling a call event with reply:

```erlang
handle_common({call,From}, code_length, #{code := Code} = Data) ->
    {keep_state, Data,
     [{reply,From,length(Code)}]}.
```

**Example 3** (statem.md, "State Time-Outs"): Handling a state_timeout event:

```erlang
open(state_timeout, lock, Data) ->
    do_lock(),
    {next_state, locked, Data}.
```

**Example 4** (statem.md, "Inserted Events"): Handling an internal event:

```erlang
locked(internal, {button,Button}, #{code := Code} = Data) ->
    ...
```

# Common Errors

- **Error**: Trying to generate an `internal` event from outside the state machine.
  **Correction**: "The internal type can only be generated through action next_event. Hence, it cannot come from an external source."

- **Error**: Forgetting to reply to `{call, From}` events.
  **Correction**: Call events require a reply via `{reply, From, Reply}` action or `gen_statem:reply/1,2`. The caller will block until a reply is received (or timeout).

# Common Confusions

- **Confusion**: `info` events require special handling to receive.
  **Clarification**: Any regular Erlang message sent to the gen_statem process (not through `cast` or `call`) is automatically delivered as an `info` event. This includes messages from `erlang:send_after/3`, monitor notifications, etc.

- **Confusion**: All event types besides `internal` can be generated with `next_event`.
  **Clarification**: "All event types above can also be generated using the next_event action: `{next_event, EventType, EventContent}`." This means you can insert cast, call, info, or timeout events to yourself, though `internal` is the most common use case.
