# Quick Definition

A boot script specifies which code to load and which applications to start when the Erlang runtime system is started, generated from a .rel file by `systools:make_script/1,2`.

# Core Definition

According to the OTP Design Principles "Releases" chapter: "`systools` in the SASL application includes tools to build and check releases. The functions read the `.rel` and `.app` files and perform syntax and dependency checks. The `systools:make_script/1,2` function is used to generate a boot script." The function creates both a human-readable boot script (`Rel.script`) and a binary boot script (`Rel.boot`) used by the runtime system. When Erlang/OTP is started using a boot script, all applications from the .rel file are automatically loaded and started.

# Prerequisites

- **Release** -- A boot script is generated for a specific release.
- **Release Resource File** -- The .rel file and all referenced .app files serve as input for boot script generation.

# Key Properties

1. Generated by `systools:make_script/1,2` from a .rel file.
2. Produces two files: a human-readable `.script` file and a binary `.boot` file.
3. The binary .boot file is what the runtime system actually uses at startup.
4. Automatically loads and starts all applications listed in the .rel file.
5. The `local` option generates paths relative to local application directories (useful for testing).
6. Without the `local` option, paths use `$ROOT/lib` (needed for deployment).
7. In a release package, the boot script is renamed to `start.boot`.

# Construction / Recognition

## To Construct/Create:
1. Ensure the .rel file and all referenced .app files are available on the code path.
2. Call `systools:make_script("RelName")` (without `.rel` extension).
3. Optionally use `systools:make_script("RelName", [local])` for local testing.

## To Identify/Recognize:
1. Files with `.script` (human-readable) or `.boot` (binary) extensions.
2. Named `start.boot` when found inside a release package.
3. Referenced via the `-boot` flag when starting `erl`.

# Context & Application

Boot scripts are essential for both development testing and production deployment. During development, the `local` option allows testing the boot sequence against locally available applications. For production, boot scripts without `local` are packaged into release packages, ensuring all paths are relative. The boot script is also critical for release handling: information about applications is fetched from the script during upgrades and downgrades.

# Examples

**Example 1** (release_structure.md, "Generating Boot Scripts"): Generating a boot script with the `local` option for local testing:

```text
1> systools:make_script("ch_rel-1", [local]).
ok
```

Starting the system with the generated boot script:

```text
% erl -boot ch_rel-1
```

This automatically loads and starts all four applications (kernel, stdlib, sasl, ch_app).

**Example 2** (release_structure.md, "Creating a Release Package"): When creating a release package, a new boot script is generated without the `local` option:

```erlang
1> systools:make_script("ch_rel-1").
ok
2> systools:make_tar("ch_rel-1").
ok
```

The boot script is included in the release package as `releases/A/start.boot`.

# Common Errors

- **Error**: Using a boot script generated with the `local` option in a release package.
  **Correction**: The release package must contain a boot script generated without the `local` option, as hard-coded absolute paths are not allowed since the installation directory is unknown at packaging time.

- **Error**: Generating the boot script from a different .rel file than the one used for the release package.
  **Correction**: The boot script must be generated from the same .rel file as the release package, because application information is fetched from the script during upgrades.

# Common Confusions

- **Confusion**: Thinking the .script file (human-readable) is what the runtime uses.
  **Clarification**: The runtime system uses the binary .boot file. The .script file is the human-readable version useful for inspection and debugging.
