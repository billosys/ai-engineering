# Quick Definition

A release upgrade file (relup) defines how to upgrade and downgrade between the new and previous versions of an entire release, containing a single ordered list of low-level instructions generated from the .appup files of all involved applications.

# Core Definition

According to the OTP Design Principles "Release Handling" chapter: "To define how to upgrade/downgrade between the new version and previous versions of a release, a _release upgrade file_, or in short `.relup` file, is to be created." The file is typically generated by `systools:make_relup/3,4`, which takes the relevant .rel files, .app files, and .appup files as input. It deduces which applications are to be added, deleted, upgraded, or downgraded. The instructions from .appup files are fetched, transformed into low-level instructions, and placed in the correct order in a single list. The relup file can also be created manually if relatively simple, but it must only contain low-level instructions.

# Prerequisites

- **Release Handling** -- The relup file is a core artifact of the release handling framework.
- **Application Upgrade File** -- .appup files for each modified application are needed as input.
- **Release Resource File** -- Both old and new .rel files are needed for generation.

# Key Properties

1. Generated by `systools:make_relup/3,4` or created manually.
2. Named simply `relup` (no application-specific prefix).
3. Contains only low-level instructions (high-level instructions from .appup files are translated).
4. Instructions are ordered correctly to handle dependencies.
5. Automatically determines which applications to add, delete, upgrade, or downgrade by comparing .rel files.
6. Both old and new .rel, .app, .appup, and .beam files must be on the code path during generation.
7. Automatically included in the release package if present.
8. All release versions except the first must contain a relup file.

# Construction / Recognition

## To Construct/Create:
1. Ensure .appup files exist for all modified applications.
2. Ensure both old and new .rel and .app files are on the code path.
3. Call `systools:make_relup("NewRel", ["OldRel1", ...], ["OldRel1", ...])`.
4. Use the `path` option to extend the code path if needed.

## To Identify/Recognize:
1. A file named `relup` (no extension) in the `releases/Vsn/` directory.
2. Contains upgrade and downgrade instructions between specific release versions.

# Context & Application

The relup file is the single artifact that the release handler evaluates during an upgrade or downgrade. It coordinates changes across all applications in the release. While `systools:make_relup` generates it automatically, complex scenarios (like changing included applications) may require manual creation or editing of the relup file. Understanding the relationship between .appup files (per-application, high-level) and the relup file (per-release, low-level) is essential.

# Examples

**Example 1** (release_handling.md, "Release Upgrade File"): Generating a relup file for upgrading from `ch_rel-1` (version "A") to `ch_rel-2` (version "B"):

```text
1> systools:make_relup("ch_rel-2", ["ch_rel-1"], ["ch_rel-1"]).
ok
```

With extended code path:

```text
1> systools:make_relup("ch_rel-2", ["ch_rel-1"], ["ch_rel-1"],
   [{path,["../ch_rel-1",
   "../ch_rel-1/lib/ch_app-1/ebin"]}]).
ok
```

# Relationships

## Builds Upon
- **Application Upgrade File** -- Instructions from .appup files are transformed and merged into the relup.
- **Release Resource File** -- Old and new .rel files determine which applications changed.

## Enables
- **Installing a Release** -- The release handler evaluates the relup file instructions during installation.

## Related
- **Release Handler** -- Reads and evaluates the relup file.
- **Release Handling Instructions** -- The relup contains low-level instructions.
- **Release Package** -- The relup is included in the release package.

## Contrasts With
- **Application Upgrade File** -- .appup files are per-application with high-level instructions; the relup is per-release with low-level instructions. .appup files are authored manually; the relup is typically generated.

# Common Errors

- **Error**: Not having old .rel and .app files on the code path when generating the relup.
  **Correction**: Both old and new versions of .rel, .app, .appup, and .beam files must be available. Use the `path` option to specify additional directories.

- **Error**: Forgetting to include the relup file in the release package.
  **Correction**: If the relup file is present when `systools:make_tar` is called, it is automatically included. Ensure it is generated before creating the release package.

# Common Confusions

- **Confusion**: Thinking the relup file contains the same format as .appup files.
  **Clarification**: The relup file contains only low-level instructions. High-level instructions from .appup files (like `{update, Module, supervisor}`) are translated by `systools:make_relup` into sequences of low-level instructions (suspend, code_change, load, resume, etc.).
