# Quick Definition

An app file is the metadata file every OTP application carries; it declares the application's name, version, dependencies, modules, and (for regular applications) its callback module.

# Core Definition

From Chapter 1, section "OTP Applications": "Each OTP application should contain an *app file*, either `ebin/<AppName>.app` or more often, `src/<AppName>.app.src`." A build system generates the final file that goes in `ebin`; many `src/<AppName>.app.src` files do not list modules and let the build system fill them in.

There are two main varieties of app file. A library-application app file:

```erlang
{application, useragent, [
  {description, "Identify browsers & OSes from useragent strings"},
  {vsn, "0.1.2"},
  {registered, []},
  {applications, [kernel, stdlib]},
  {modules, [useragent]}
]}.
```

And a regular-application app file, which additionally carries a `mod` tuple:

```erlang
{application, dispcount, [
  ...
  {mod, {dispcount, []}},
  ...
]}.
```

# Prerequisites

- `otp-application` — the app file is a property of an OTP application.

# Key Properties

1. Located at `ebin/<AppName>.app` or, more commonly, the source form `src/<AppName>.app.src`.
2. The `ebin/<AppName>.app` form is generated by the build system from the `.app.src` source.
3. Declares `description`, `vsn` (version), `registered` names, `applications` (dependencies), and `modules`.
4. The presence or absence of a `{mod, {Module, Args}}` tuple distinguishes a regular application from a library application.
5. Because OTP applications share no state, dependency relationships can be read from the `applications` list in app files alone.

# Construction / Recognition

To use it when diving into a code base: open the app file, read `description` and `vsn` for identity, read `applications` to learn dependencies, and check for `mod` to determine whether the application starts a process. The `app_deps.erl` script in `recon` generates a dependency diagram from app files.

# Context & Application

The app file is the primary documentation-by-structure of an OTP application. It is what dependency-graph tooling reads, and what the OTP runtime uses to know what to start.

# Examples

From Chapter 1, section "OTP Applications": the `useragent` app file (library variety, no `mod`) and the `dispcount` app file (regular variety, with `{mod, {dispcount, []}}`) are given side by side as the two varieties.

# Common Errors

- Editing the generated `ebin/<AppName>.app` instead of the `src/<AppName>.app.src` source — the build system will overwrite it.

# Common Confusions

- The `applications` tuple lists *dependencies*, not sub-applications; it is not the release manifest.
- An `.app.src` file without a `modules` list is not malformed — the build system supplies the module list.
