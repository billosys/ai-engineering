# Quick Definition

The `.script` file is a full specification of how to start a release, and the `.boot` file is its binary form — the file the Erlang runtime reads when it boots.

# Core Definition

The `.rel` file is where it all starts, but is not enough to start a running target system. The next step is to create two files that represent a more complete specification: the `.script` and `.boot` files. The `.script` file contains a full specification of what will be included in applications — paths to applications, which modules will be loaded, and other necessary information. The `.boot` file is a binary representation of the `.script` file that is read by the Erlang runtime system when it boots. Both are generated with `systools:make_script/2` from the SASL application ("Erlang and OTP in Action," Ch. 10, Section 10.2.4).

# Prerequisites

- **.rel file** — The boot script is generated from the release metadata file.
- **Erlang release** — Boot files are part of producing a runnable release.

# Key Properties

1. The `.script` file is human-readable Erlang terms describing the entire boot process.
2. The `.boot` file is the binary form actually read at VM boot time.
3. Generated by `systools:make_script(Release, Options)`, part of SASL.
4. `systools:script2boot(Release)` regenerates the `.boot` file after manual `.script` edits.
5. The `local` option writes absolute paths to all applications — good for testing, not portable.
6. Without `local`, the files expect applications under a `lib` directory pointed to by the `$ROOT` system variable — suitable for installable, host-independent releases.

# Construction / Recognition

## To Construct/Create:
1. Start `erl` with `-pa` flags adding code paths to all the release's applications.
2. Run `systools:make_script("Release", Options)` from the directory containing the `.rel` file.
3. Use the `local` option for local testing, or omit it for a location-independent release.
4. This produces `Release.script` and `Release.boot`.

## To Identify/Recognize:
1. A `.script` file begins with a comment `%% script generated at ...` and a `{script, ...}` tuple.

# Context & Application

- **Typical contexts**: Generating the runnable form of a release.
- **Common applications**: The `.boot` file is passed to `erl` via the `-boot` flag to start a target system.
- **Historical/stylistic notes**: In a release package the boot file is renamed `start.boot` inside the `releases/<version>` directory.

# Examples

**Example 1** (Section 10.2.4): `systools:make_script("simple_cache", [local])` generates `simple_cache.script` and `simple_cache.boot` in the current directory.

**Example 2** (Section 10.3.1): Re-running `systools:make_script("simple_cache", [])` without `local` produces a location-independent boot script suitable for packaging.

# Relationships

## Builds Upon
- **.rel file** — The release metadata file is the input to `make_script`.

## Enables
- **Target system** — A target system is started from a `.boot` file.
- **Release package** — The boot file is bundled into the package.

## Related
- **sys.config** — Passed alongside the boot file when starting the system.

## Contrasts With
- **.rel file** — The `.rel` file is a high-level spec; the boot script is the complete, low-level startup specification.

# Common Errors

- **Error**: Using a `local`-option boot file on a different machine or after moving code.
  **Correction**: The `local` option hardcodes absolute paths; regenerate without `local` for portable releases.

- **Error**: Generating the boot script without `-pa` paths to the release's own applications.
  **Correction**: Start `erl` with `-pa` for every application not on the default path.

# Common Confusions

- **Confusion**: Thinking the `.script` and `.boot` files are interchangeable.
  **Clarification**: `.script` is editable Erlang terms; `.boot` is the binary the VM actually reads — regenerate `.boot` from `.script` with `script2boot`.
