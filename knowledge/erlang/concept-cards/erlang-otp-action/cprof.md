# Quick Definition

`cprof` is an Erlang/OTP profiler that simply counts how many times each function is called, with very low overhead — about 10% slowdown.

# Core Definition

The `cprof` tool counts function calls. It does not provide the depth of information `fprof` does, but it is simple and straightforward to use. Its main advantage is minimal impact on the running system — profiled code becomes only about 10% slower — which makes it suitable for analyzing code running live in production if necessary. It needs no special recompilation, reloading, or debugging information. You start it (optionally for a specific module), run the code, pause it, and analyze the results, which list functions in decreasing order of call count (Chapter 14, Section 14.2.1).

# Prerequisites

- **Profiling** — `cprof` is one technique for the profiling step of performance tuning.

# Key Properties

1. Counts the number of calls to each function — nothing more.
2. Very low overhead: profiled code runs only about 10% slower.
3. Needs no special recompilation, reloading, or debugging information.
4. `cprof:start()` enables call counting for all modules; `cprof:start(Module)` limits it to one module.
5. Results from `cprof:analyse(Module)` list functions in decreasing order of call count.
6. BIFs (built-in functions) cannot be call-counted by `cprof`.
7. Suitable for use on a live production system because of its low overhead.

# Construction / Recognition

## To Construct/Create (a cprof session):
1. Compile and load the module to profile (e.g. `c(profile_ex)`).
2. Call `cprof:start()` (or `cprof:start(Module)` to limit scope).
3. Run the code you want to measure.
4. Call `cprof:pause()` to stop counting.
5. Call `cprof:analyse(Module)` to fetch the call counts.

# Context & Application

- **Typical contexts**: Quickly finding which functions are called, and how often, including on live systems.
- **Common applications**: The book profiles the `profile_ex` module, confirming 1,001 calls each to `looper/1` and `funner/2`.
- **Historical/stylistic notes**: Presented first because it is the easiest of the standard profilers to use.

# Examples

**Example 1** (Section 14.2.1): After `cprof:start()`, running `profile_ex:run()`, `cprof:pause()`, then `cprof:analyse(profile_ex)` shows 1,001 calls to `looper/1` and `funner/2` and 1,000 to the autogenerated fun `'-funner/1-fun-0-'/1`.

**Example 2** (Section 14.2.1): Calls to the BIF `integer_to_list/1` do not appear, because BIFs cannot be call-counted.

# Relationships

## Related
- **fprof** — The deeper, heavier execution-time profiler used when call counts are not enough.

## Contrasts With
- **fprof** — `cprof` only counts calls with ~10% overhead; `fprof` measures execution time with up to 10x overhead.

# Common Errors

- **Error**: Expecting `cprof` to report BIF call counts.
  **Correction**: BIFs cannot be call-counted; use a different approach for them.

- **Error**: Forgetting to `pause` before analyzing.
  **Correction**: Pause counting once the measured code has finished, then analyze.

# Common Confusions

- **Confusion**: Thinking `cprof` reports time spent in functions.
  **Clarification**: It only counts calls; for time use `fprof`.
