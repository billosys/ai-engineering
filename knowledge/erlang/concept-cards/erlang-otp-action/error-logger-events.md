# Quick Definition

Error logger events are the specific tagged tuples the `error_logger` functions generate and post to the logger's event manager — one shape per message/report function — which handlers match in `handle_event/2`.

# Core Definition

The `error_logger` functions generate a fixed set of event tuples that are posted to the `error_logger` event manager, where handlers receive them via `handle_event/2`. Each tuple has the form `{Tag, Gleader, Payload}`. The six tags and their payloads (Ch. 7, Table 7.1) are:

- `{error, Gleader, {Pid, Format, Data}}` — from `error_msg()`
- `{error_report, Gleader, {Pid, Type, Report}}` — from `error_report()`
- `{warning_msg, Gleader, {Pid, Format, Data}}` — from `warning_msg()`
- `{warning_report, Gleader, {Pid, Type, Report}}` — from `warning_report()`
- `{info_msg, Gleader, {Pid, Format, Data}}` — from `info_msg()`
- `{info_report, Gleader, {Pid, Type, Report}}` — from `info_report()`

`Gleader` is the group leader, indicating where to send standard output (it can usually be ignored). For report events called without an explicit type, the `Type` field is `std_error`, `std_warning`, or `std_info` respectively; other type identifiers indicate user-defined report types.

# Prerequisites

- **error_logger** — These events are what the `error_logger` functions produce.
- **event-handler** — Handlers consume these events.

# Key Properties

1. Six event-tuple shapes, one per `error_logger` function family.
2. Each tuple has the form `{Tag, Gleader, Payload}`.
3. `*_msg` events carry `{Pid, Format, Data}`; `*_report` events carry `{Pid, Type, Report}`.
4. `Gleader` is the group leader; usually ignored.
5. Untyped reports get `std_error`/`std_warning`/`std_info` as their `Type`.
6. Handlers may also receive other (system) messages and need a catch-all.

# Construction / Recognition

## To Match Error Logger Events:
1. Write `handle_event/2` clauses pattern-matching the six tuple shapes.
2. Distinguish standard report types (`std_error` etc.) from user-defined types with separate clauses.
3. Bind `Pid`, `Format`/`Type`, and `Data`/`Report` and act on them.

## To Recognize:
1. A three-element tuple tagged `error`, `error_report`, `warning_msg`, `warning_report`, `info_msg`, or `info_report`.

# Context & Application

- **Typical contexts**: Inside `gen_event` handlers attached to the `error_logger` process.
- **Common applications**: Custom log formatting and routing.
- **Historical/stylistic notes**: The modern `*_report` functions are what allow user-defined report types.

# Examples

**Example 1** (Section 7.2.3, Table 7.1): The event `{info_msg, Gleader, {Pid, Format, Data}}` is the tuple generated by a call to `error_logger:info_msg/2`.

# Common Errors

- **Error**: Matching only `*_msg` events and ignoring `*_report` events.
  **Correction**: Handle all six tuple shapes, plus a catch-all for system messages.

# Common Confusions

- **Confusion**: Thinking `Gleader` carries useful payload data.
  **Clarification**: `Gleader` is the group leader for output redirection; it can be ignored for most handlers.
