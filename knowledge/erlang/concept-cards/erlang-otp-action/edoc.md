# Quick Definition

EDoc is the standard Erlang/OTP tool for generating documentation directly from source-code annotations, similar to Javadoc. Annotations are `@`-prefixed tags in comments.

# Core Definition

EDoc is a tool for generating documentation directly from source-code annotations (similar to Javadoc) and comes with the standard Erlang/OTP distribution (Ch. 3, Section 3.2.2). It is the de facto standard for in-code Erlang documentation. All EDoc tags begin with an `@` character. Basic tags include `@author`, `@copyright`, `@doc` (general documentation text whose first sentence is used as a summary; may contain XHTML and some wiki markup), `@end` (ends the tag above it), and `@spec` (describes the input and return types of a function). For an OTP application, documentation is generated by calling `edoc:application/3` (or `edoc:application/1`) from the Erlang shell, producing `doc/index.html` and other files. EDoc works even with no annotations, producing a basic listing of modules and exported functions.

# Prerequisites

- **Erlang module** — EDoc reads annotations from module source files.

# Key Properties

1. Ships with the standard Erlang/OTP distribution.
2. Generates documentation from `@`-prefixed annotations in comments.
3. `@doc`'s first sentence is used as the summary description.
4. `@spec` describes a function's input and return types.
5. `edoc:application/3` / `edoc:application/1` generates docs for a whole application.
6. Works even with no annotations, listing modules and exported functions.

# Construction / Recognition

## To Generate EDoc:
1. Annotate modules and functions with `@author`, `@copyright`, `@doc`, `@spec`, `@end`.
2. From the Erlang shell, call `edoc:application(AppName, ".", [])` (three-argument form).
3. Or, with the code path set up, call `edoc:application(AppName)` (one-argument form).
4. Open the generated `doc/index.html` in a browser.

# Context & Application

EDoc lets documentation live with the code and stay current. It is recommended that every API function and the module as a whole carry at least a `@doc` annotation.

- **Typical contexts**: Documenting OTP applications and their public APIs.
- **Common applications**: Generating `doc/index.html` for the `tcp_rpc` application.

# Common Errors

- **Error**: Omitting the directory argument to `edoc:application/3` when the code path uses a relative `ebin` path.
  **Correction**: Pass `"."` (or use the one-argument form once paths give enough clues).

# Common Confusions

- **Confusion**: Thinking EDoc needs annotations to produce anything.
  **Clarification**: It works without annotations, generating a basic listing of modules and exported functions.
