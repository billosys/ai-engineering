# Quick Definition

The `restart_emulator` instruction is a release upgrade directive that causes the Erlang runtime system to restart with the new versions of all applications at once, providing a simpler but more "brutal" alternative to the two-step `restart_new_emulator` approach.

# Core Definition

If the more brutal variant is preferred, the release upgrade file can be handwritten using only the single upgrade instruction `restart_emulator`. This instruction, in contrast to `restart_new_emulator`, causes the runtime system to restart with the new versions of all applications. Instructions included before `restart_emulator` in a handwritten relup file execute in the old runtime system, which carries a significant risk since there is no guarantee that new BEAM code can be loaded into the old runtime. Instructions added after `restart_emulator` have no effect, as the `release_handler` will not execute them.

# Prerequisites

- Understanding of `restart_application` and standard application upgrades

- Familiarity with release upgrade files (relup) and the `release_handler`

# Key Properties

1. Restarts the runtime system with new versions of ALL applications simultaneously
2. The source documentation explicitly calls it the "more brutal variant"
3. Instructions placed before `restart_emulator` execute in the old runtime system, which is risky
4. Instructions placed after `restart_emulator` are never executed by the `release_handler`
5. Typically requires a handwritten relup file (not auto-generated by `systools:make_relup`)
6. The only viable option for upgrading applications that do not support code upgrade (empty appup files)

# Construction / Recognition

## To Construct/Create:
1. Handwrite a relup file containing only the `restart_emulator` instruction
2. Do not place any other instructions in the file (instructions before it are risky; instructions after it are ignored)

## To Identify/Recognize:
1. Look for `restart_emulator` as the sole instruction in a handwritten relup file
2. Distinguishable from `restart_new_emulator` by loading ALL new application versions during the restart

# Context & Application

The `restart_emulator` instruction is used when the controlled two-step approach of `restart_new_emulator` is unnecessary or impractical. It is particularly relevant when upgrading applications that do not support code upgrade at all (those with empty appup files like `{Vsn,[],[]}`, such as Erl_interface). In such cases, `systools:make_relup` will fail, and the only option is to handwrite a relup file using `restart_emulator`.

# Examples

**Example 1** (forced upgrade): For applications like Erl_interface that ship with empty appup files (`{Vsn,[],[]}`), attempting to generate a relup with `systools:make_relup` fails. The workaround is to handwrite the relup file with only `restart_emulator` as the instruction, causing a complete restart with all new application versions.

**Example 2** (unsafe instruction ordering): If a handwritten relup includes instructions before `restart_emulator`, those instructions run in the old runtime system. This is dangerous because new BEAM code may not be loadable in the old runtime. For example, placing a `load_module` instruction before `restart_emulator` could fail if the new module uses features unavailable in the old runtime.

# Common Errors

- **Error**: Placing upgrade instructions after `restart_emulator` and expecting them to execute
  **Correction**: The `release_handler` does not execute any instructions after `restart_emulator`. All upgrade logic must be handled by the restart itself.

- **Error**: Placing instructions before `restart_emulator` that attempt to load new BEAM code
  **Correction**: There is no guarantee that new BEAM code can be loaded into the old runtime system. Avoid placing any instructions before `restart_emulator`.

# Common Confusions

- **Confusion**: `restart_emulator` is just a synonym for `restart_new_emulator`
  **Clarification**: They are fundamentally different. `restart_new_emulator` loads only new core applications during the restart and then executes further upgrade instructions. `restart_emulator` loads all new applications during the restart and ignores any subsequent instructions.

- **Confusion**: `restart_emulator` is generated automatically by `systools:make_relup`
  **Clarification**: The auto-generated relup uses `restart_new_emulator` for core upgrades. Using `restart_emulator` requires handwriting the relup file.
