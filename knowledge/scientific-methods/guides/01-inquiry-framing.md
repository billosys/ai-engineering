# Inquiry Framing

Use inquiry framing when the user has a hunch, concern, disagreement, or broad
curiosity that needs to become a testable investigation.

## Start With The Decision

Ask what the result will decide. A good experiment is not merely interesting;
it changes what someone will do next.

Capture:

- the question;
- the decision the answer informs;
- the current belief or hypothesis;
- what result would change the decision;
- what result would leave the decision unchanged.

If no decision is at stake, treat the work as exploration and say so.

## Turn Questions Into Claims

Prefer claims that can be contradicted by evidence:

- Fuzzy: "Is the new framework better?"
- Testable: "For the same bounded implementation task, the new framework
  produces a more complete plan, fewer uncontrolled scope expansions, and a
  better audit handoff than the old framework."

The claim does not need to be numerical. It does need observable consequences.

## Define Scope

Name what is in scope and what is not. A narrow test usually teaches more than
a broad comparison with unclear causes.

Record:

- object of study;
- population or task family;
- time/version boundary;
- excluded cases;
- expected use of the result.

## Separate Exploration From Confirmation

Exploration finds variables, examples, and possible measures. Confirmation
tests a predeclared protocol. Mixing them is allowed only if the report names
which findings were discovered during the run and which were tested under the
original design.

## Framing Checklist

- What decision will this inform?
- What claim is being tested?
- What would count as contrary evidence?
- What is the smallest useful task or sample?
- What must not be generalized from this run?
