# Analysis And Threats To Validity

Use analysis and threats-to-validity guidance when turning results into a
decision without overstating what the experiment proved.

## Analysis Layers

Keep four layers separate:

1. Raw result: what each condition produced.
2. Measured result: how each result scored or passed gates.
3. Interpretation: what the difference suggests.
4. Decision: what to do next.

Do not skip from raw result to decision without naming the interpretation.

## Threats To Validity

**Internal validity.** Did the variable under test cause the difference, or did
another difference between conditions explain it?

**External validity.** Does this result generalize beyond the tested task,
repository, model, or user?

**Construct validity.** Did the measures actually capture the quality being
claimed?

**Conclusion validity.** Is the evidence strong enough for the conclusion, or
is the pattern underdetermined?

**Operational validity.** Did the run follow the protocol closely enough that
the result can be trusted?

## Conclusions

Use calibrated conclusions:

- "This run supports..."
- "This run did not show..."
- "This is a regression for..."
- "This remains ambiguous because..."
- "The next test should..."

Avoid "proved" unless the design and evidence genuinely warrant it.

## Analysis Checklist

- What did the data show?
- What decision does that support?
- What are the strongest alternative explanations?
- What should not be generalized?
- What would you test next?
