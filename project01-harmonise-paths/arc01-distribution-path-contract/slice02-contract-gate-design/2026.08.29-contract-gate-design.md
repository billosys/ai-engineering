# Contract Gate Design - 2026.08.29

Slice: `project01-harmonise-paths/arc01-distribution-path-contract/slice02-contract-gate-design`

## Summary

Slice 01 established the package path problem with CDC verification: 145
actionable package-context misses across the 12 generated install zips. The
validated classes are `bundled-reference`, `source-clone-reference`,
`repo-only/provenance`, `example-project path`, `external URL`, and
`parser false positive`.

This design turns that contract into the gate Slice 03 should implement. The
gate must be Make-owned, Markdown-aware, and evidence-stable. It must not be a
raw regex hard gate, and future reports must not claim that filtered CSV output
contains classes, such as external URL, that the checker intentionally
suppresses or skips.

## Validation Surface

Primary validation surface: generated zip archives named by `INSTALL_ZIPS`.

Rationale: the project definition of done is about actual distributable
packages. A source-only scan can miss staging transforms and packaging layout
effects. A staging-directory scan is useful for implementation debugging but is
not authoritative because the current `pack_skill` and `collab-framework`
targets remove `build/` after each archive is written.

Slice 03 should implement the final gate over generated zip files:

```sh
make check-package-paths
```

The Make target should depend on or invoke `all` so the generated zip set is
current before the checker runs. If Slice 03 wants a faster developer-only
debug mode, it may add a script option that accepts an existing staging
directory, but the Make target's pass/fail result must be based on generated
zip contents.

## Make and Script Entry Points

Chosen Make target:

```make
check-package-paths
```

Chosen checker entry point:

```text
scripts/check-package-paths
```

`scripts/check-package-paths` should be a small checked-in Python 3 script with
no `.py` suffix. The no-suffix path avoids the current repository ignore rule
for `/scripts/*.py` while keeping the entry point next to existing repository
scripts. The Make target owns orchestration; the script owns zip inspection,
Markdown parsing, classification, and report output.

Proposed Make integration for Slice 03:

```make
.PHONY: check-package-paths

check-package-paths: all
	@./scripts/check-package-paths \
		--exceptions package-path-exceptions.tsv \
		$(INSTALL_ZIPS)
```

Exit codes:

| Code | Meaning |
|-----:|---------|
| 0 | no hard failures; warnings and explicit exceptions may be present and reported |
| 1 | hard package-path failures found |
| 2 | invocation, unreadable zip, unreadable exception file, or malformed exception schema |

The checker should emit a stable human-readable summary to stdout and a
machine-readable TSV or JSON report only if Slice 03 explicitly adds that
option. Any emitted report must include counts for skipped classes directly;
it must not derive external URL counts from a CSV stream that filtered URLs
out before writing.

## Implementation Style

Use a Make-facing checked-in parser script.

Pure Make/Bash is the wrong boundary for this gate because the design requires
zip introspection, path normalization, Markdown-aware parsing, classification,
and structured exception matching. Bash is still appropriate for invoking the
checker from Make and preserving the repository's packaging workflow.

The script should use only Python standard library modules if feasible:

- `zipfile` for generated zip inspection;
- `pathlib` and `posixpath` for path normalization;
- `urllib.parse` for URL scheme handling;
- either a small Markdown scanner state machine or a vendored-free parser
  strategy implemented in the script.

If Slice 03 decides a third-party Markdown parser is needed, it should record
that as a deliberate dependency decision instead of silently adding a package
manager requirement.

## Classification Behavior

The checker must assign every observed reference to one of these classes or
fail as an unclassified internal checker error.

| Classification | Default behavior | Definition | Notes |
|----------------|------------------|------------|-------|
| bundled-reference | hard fail when unresolved; pass when resolved | Target is intended to exist inside the package. | Transitional warnings are allowed only through an explicit exception row while Arc 02 harmonisation has not landed. |
| source-clone-reference | warning or explicit exception | Target exists in the source clone but not in the package. | Must be marked as source-clone-only, repo-only, or provenance if it remains in packaged Markdown. |
| repo-only/provenance | pass only with explicit exception | Target intentionally belongs to source, planning, workbench, source corpus, extraction metadata, or provenance material. | Missing reason is a hard failure. |
| example-project path | pass only with explicit exception | Path belongs to an example project, user project, generated fixture, or illustrative tree. | Should include a reason naming why package resolution is not expected. |
| external URL | pass/skipped for package path resolution | `http://`, `https://`, `mailto:`, and similar URLs. | No network access. Count as skipped external URLs if reported. |
| parser false positive | should not be emitted in normal operation | A token the checker should avoid by Markdown-aware parsing. | Any emitted false-positive class in normal mode is a warning that parser rules need tightening. |
| unclassified | hard fail | The checker saw a path-like reference it cannot classify. | No unclassified miss bucket is allowed. |

Initial policy for current repository state:

- unresolved `bundled-reference` findings should be hard failures unless
  allowlisted as transitional warnings;
- unresolved `source-clone-reference` findings should be warnings unless
  explicitly marked as permanent repo-only/provenance exceptions;
- malformed or missing exception rows are hard failures;
- unparseable archives or Markdown decoding errors are hard failures;
- external URLs pass without network checks;
- parser false positives should be reduced by parsing rules, not hidden under
  a large exception list.

## Exception Schema

Proposed repository path:

```text
package-path-exceptions.tsv
```

This top-level TSV keeps the policy visible beside the Makefile and avoids
requiring YAML/TOML dependencies. Slice 03 may choose JSON if nested structure
becomes necessary, but the initial gate should prefer a line-oriented,
diff-friendly file.

Required columns:

```text
package	document	target	classification	disposition	reason	source	expires
```

Column rules:

| Column | Required value |
|--------|----------------|
| `package` | Zip filename or package-root glob, for example `javascript-deno-guidelines.zip`. |
| `document` | Markdown path inside the zip, relative to package root, or a narrow glob. |
| `target` | Exact target string after Markdown unescaping, or a narrow glob. |
| `classification` | One Slice 01 class: `bundled-reference`, `source-clone-reference`, `repo-only/provenance`, `example-project path`, `external URL`, or `parser false positive`. |
| `disposition` | `warning`, `explicit-exception`, or `transitional-warning`. |
| `reason` | Human-readable reason; empty reason is invalid. |
| `source` | Evidence source such as `slice01-cdc`, `slice02-design`, or issue/commit pointer. |
| `expires` | Re-entry condition such as `after-arc02`, `after-slice03`, `none`, or an issue ID. |

Policy:

- `explicit-exception` is allowed only for `repo-only/provenance`,
  `example-project path`, and intentionally skipped `external URL` rows.
- `transitional-warning` is allowed for current `bundled-reference` or
  `source-clone-reference` misses while Arc 02 has not harmonised source and
  package paths.
- `parser false positive` exceptions should be rare. A broad false-positive
  allowlist means the parser is not yet good enough for a hard gate.
- Exceptions must be exact or narrowly globbed. Whole-package wildcards are
  invalid unless the reason names a bounded package-level policy.

## Markdown-Aware Parsing Requirements

The checker must parse enough Markdown structure to avoid Slice 01's raw regex
failure mode.

Required behavior:

- scan inline link destinations: `[text](target)` and image links;
- scan reference definition destinations: `[id]: target`;
- resolve relative paths from the Markdown document's package location;
- treat same-document anchors like `#heading` as package-path pass/skipped;
- for `path#anchor`, validate only the file path in Slice 03, not the anchor;
- skip fenced code blocks;
- skip indented code blocks where feasible;
- skip HTML comments;
- treat external URLs as external URL and do not perform network checks;
- treat placeholders such as `knowledge/<slug>/SKILL*.md` as explicit
  placeholder/provenance candidates, not as literal package paths;
- scan code span content only under a conservative rule: the token must look
  like a Markdown/file path with a slash or known filename and not be a bare
  identifier from code examples.

Code span policy:

The checker may report code span path misses as warnings in Slice 03, but they
should not become hard failures until the parser has proved it can avoid the
Slice 01 false-positive pattern. Link and reference-definition destinations
are the first hard-fail surface.

Path normalization:

- use POSIX separators inside zips;
- reject resolved paths that escape the package root with `..`;
- strip query and fragment components before file existence checks;
- preserve the raw target string in reports for evidence;
- report both raw target and resolved package path.

## Source Edit Versus Staging-Time Transform

Use source edits when one source spelling improves both contexts:

- broken relative links inside `docs/pm/*` that should point to bundled
  `docs/**`;
- guide-local links that can naturally be written as `guides/...` or
  document-relative paths;
- prose that should explicitly say a path is source-clone-only, repo-only, or
  provenance.

Use staging-time transform when the source text is correctly source-rooted but
the package layout intentionally strips the source prefix:

- `knowledge/<domain>/guides/...` in packaged `SKILL.md` files;
- high-volume mature guide references where bulk source edits would churn
  stable prose;
- collaboration-framework references to domain guides that are useful in the
  source clone but not bundled in the collaboration package.

The checker should validate the generated result, not just the authored
source, so staging-time transforms remain accountable.

## Package Layout Change Boundaries

Do not expand package layout to make every source-clone reference resolve.
Package layout changes are appropriate only when the missing target is a
reader-facing bundled dependency of the skill.

Do not bundle these categories by default:

- `workbench/**`;
- `docs/dev/**`;
- extraction metadata;
- source corpora;
- maintenance-only tools;
- planning artifacts;
- full CCDP distribution materials before Arc 03.

If a future package layout change is proposed, it should include size impact,
reader value, and whether the file is required at skill runtime or only useful
for repository development.

## CCDP and Protocol Reservation

Slice 03 should reserve the classification and exception path for CCDP but
must not add CCDP package targets. Current `check-package-paths` scope should
be the generated skill zips named by `INSTALL_ZIPS`.

When Arc 03 creates a CCDP package target, it should reuse the same checker
contract:

- generated package artifact as the authoritative surface;
- package-root-relative bundled references;
- explicit repo-only/provenance/example exceptions;
- no network URL checks;
- stable report counts that do not hide filtered classes.

## Slice 03 Implementation Scope

Slice 03 should implement:

- `make check-package-paths`;
- `scripts/check-package-paths`;
- `package-path-exceptions.tsv` if current known exceptions are needed for an
  initially non-breaking gate;
- generated-zip scanning for every archive named by `INSTALL_ZIPS`;
- Markdown-aware parsing for inline links, image links, reference definitions,
  conservative code spans, anchors, placeholders, and external URLs;
- classification and report output for all Slice 01 classes;
- hard-fail/warning/explicit-exception behavior;
- tests or reproducible fixtures sufficient to prove parser behavior and
  current package scan behavior;
- integration of the target into the appropriate packaging or install flow
  after the target can run repeatably.

Slice 03 non-goals and out of scope:

- editing mature language guide prose;
- harmonising the 145 current actionable misses beyond the minimum needed to
  make the gate runnable under an explicit transitional policy;
- adding CCDP package targets;
- changing zip layout;
- moving source directories;
- implementing URL liveness checks;
- treating raw regex output as a hard-fail parser.

## Acceptance Design for Slice 03

The implementation slice should be accepted when:

- `make check-package-paths` rebuilds or verifies current generated zip
  artifacts and runs the checker;
- every emitted finding has a classification;
- hard failures are nonzero exit 1;
- warnings and explicit exceptions are visible in the summary;
- external URL references are counted as skipped or explicitly omitted without
  claiming they came from a filtered CSV;
- a malformed exception row causes exit 2;
- the report clearly separates hard failures, warnings, explicit exceptions,
  skipped external URLs, and parser-suppressed material.

Recommended initial output shape:

```text
package path check
zips scanned: 12
markdown files scanned: <n>
hard failures: <n>
warnings: <n>
explicit exceptions: <n>
skipped external URLs: <n>
parser-suppressed code/example tokens: <n or omitted>
```

If parser-suppressed counts are omitted, the output should say `not emitted`
rather than implying a zero count.
