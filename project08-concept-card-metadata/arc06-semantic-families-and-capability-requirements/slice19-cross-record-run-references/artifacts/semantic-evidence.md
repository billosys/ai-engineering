## Documented rules, observations, inferences and unknowns

Documented rules from the prompt and source guidance:

- `run_refs` is interpreted in its containing record kind; repeated spelling
  does not create one cross-kind authority.
- Root, sequence, element and child states are distinct.
- Relative paths are resolved from the containing record in the authoritative
  evidence tree. Preserved rerun records use baseline snapshots, not ignored
  workbench bytes.
- Address resolution and target identity are separate. Exact identity requires
  target `record_type: extraction-run`, matching id and matching revision.
- Run provenance does not transfer actor, scope, method, support, evidence
  grade, validation, verification, reconciliation, preservation, admission,
  runtime or contributor authority.

Observed values:

- All eleven templates expose an empty `run_refs` sequence.
- Only concept-card and source-support records populate the root in this
  frozen population.
- All 26 populated elements are objects with string id/path and numeric
  revision; every observed revision is 1.
- Four tuples produce one exact match, two path-only addresses and one missing
  target. Historical Complete Musician/Erlang records contain zero roots in a
  bounded 2,054-record comparison.

CC inferences, kept bounded:

- In concept-card records the field is best described as candidate production
  history; in source-support records it is support-attachment production
  history. These are kind-local meanings, not a universal definition.
- The current tuple is an identity claim whose exactness depends on inspecting
  the target declaration, not on id/path/revision shape alone.

Conflicts and unresolved behavior:

- Nine kinds have only template or absent observations, so their precise event,
  requiredness and target policy remain unknown.
- Existing README targets contain descriptive run names and revisions in body
  text or surrounding card metadata, but no opening extraction-run declaration;
  they remain path-only.
- The synthetic rich-profile reference points to a target not present in the

- Multiple references, ordering, supersession, relocation, target type

## Kind-specific operational consequences

User-authored and graph-facing records (claim, competency-question,
concept-card, relationship-edge) must keep run production history separate from
claim support, CQ answerability and relation semantics. Trace/result/decision
records (memory-admission, preservation-decision, reconciliation-result,
validation-result and verification-result) must not inherit authority from a
referenced run. Source-locator and source-support records must keep address,
source span and support warrant separate from production history. Readers need
to show absent, empty, path-only and exact-match states explicitly; extractors
need to preserve raw state; queries need address and identity predicates
separately; migrations must not backfill or normalize missing provenance.
